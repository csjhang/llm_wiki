# Sub-project 4: Fusion (`wiki-fuse`) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn a Heptabase work whiteboard into a checked hypothesis page plus a hypothesis card on that board (directed mode); propose fusion candidates after an ingest creates a new mechanism (divergent mode); and re-evaluate a hypothesis with new evidence (update mode).

**Architecture:** The judgment lives in the `wiki-fuse` skill (Claude Code). Deterministic support lives in `wiki-tool fuse` commands: resolve a board to wiki pages, check a hypothesis page, and write the commit. The app gains two small pieces: a candidate generator that runs after an ingest creates a new mechanism, and two MCP tools (`llm_wiki_add_review`, `llm_wiki_resolve_review`) so the skill can read and close review items. The hypothesis card reaches Heptabase through the normal `wiki-sync` down-sync (`create` + `place` actions from sub-project 3).

**Tech Stack:** TypeScript, Rust (one API route), Node MCP server, vitest, cargo test.

**Spec:** `docs/superpowers/specs/2026-10-23-mechanism-wiki-heptabase-design.md` (sections 5.8, 8.1–8.4, 12 row 4)

## Global Constraints

- Source/target sections: a section whose title starts with `來源`, `Source`, or `source` is the source side; `目標`, `Target`, or `target` is the target side.
- Hypothesis frontmatter and sections follow `templates/mechanism-wiki/schema/page-types/hypothesis.md` and `HYPOTHESIS_SECTIONS`.
- A hypothesis page passes `wiki-tool fuse check` before it is committed. The commit subject is `fuse: <title> (1 pages)` (or `(N pages)` when the mechanism page is also updated in a reading wiki).
- A work-wiki hypothesis never edits a reading-wiki page.
- Candidate generation: at most 3 per new mechanism; the skill's explore mode shows at most 5. Dismissed candidates are stored in `.llm-wiki/fusion-dismissed.json` as `{ mechanism, targetDomain }` pairs and are never proposed again.
- `fusion-candidate` review options: `Start fusion` (action `mech:start-fusion`, which copies `/wiki-fuse --candidate <review id>` to the clipboard and keeps the item open) and `Skip` (action `mech:dismiss-fusion`).
- Commit trailer: your session's Co-Authored-By line plus `Claude-Session: https://claude.ai/code/session_013yG6txX1fFsHyk4VQiasu7`.
- Verification: `npm run test:mocks`, `npm run typecheck`, `npm run build:wiki-tool`, `npm run mcp:test`, and `cargo test --manifest-path src-tauri/Cargo.toml --lib api_server` where Rust changed.

## Review Focus

1. A board with no source/target sections and cards from three domains. Expected: `fuse resolve-board` returns `pairing: null` and the skill asks the user; it never picks silently. (Task 1 test `no sections means no pairing`.)
2. A board card that is in no wiki yet. Expected: listed as `not-ingested`, with the skill offering to add `#ingest` first. (Task 1 test `reports cards that are not ingested`.)
3. A hypothesis whose verify table has an empty "how to refute" cell. Expected: `fuse check` fails and names the row. (Task 2 test `empty refute cell fails`.)
4. A candidate the user skipped last week for the same mechanism and domain. Expected: not proposed again. (Task 4 test `dismissed pairs are not proposed`.)
5. The skill adds a review item while the app is closed. Expected: a clear error from the MCP tool, and the skill tells the user to open the app. (Task 3 test `add_review reports app offline`.)
